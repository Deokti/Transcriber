# ADR-0001. Язык приложения и стек интерфейса

**Статус:** принято · 16.09.2026
**Решение:** Python 3.12 + PySide6 (Qt 6), движок распознавания — faster-whisper

> *ADR (Architecture Decision Record) — короткая запись об одном принятом решении: что требовалось, какие были варианты, что выбрали и почему. Пишется один раз и не переписывается: если решение отменят, заводится новая запись со ссылкой на эту. Смысл в том, чтобы через полгода не спорить заново — и чтобы новый человек (или вы сами) понимал, почему всё устроено так, а не иначе.*

---

## 1. Контекст

Что уже задано требованиями:

- **NFR-1** — Windows и macOS с первого дня, Linux попутно.
- **D-2** — на macOS счёт идёт на процессоре, второй движок распознавания не пишем.
- **D-1** — сначала запуск из исходников, сборка установщика позже.
- **NFR-5** — интерфейс переводится, значит в ядре нет человеческих строк.
- Проект поддерживает **один человек**, и этот человек профессионально пишет на JS/TS (React), а не на Python.
- Есть проверенное ядро на Python (ffmpeg, распознавание, анализ качества), отработавшее на трёх часах реального аудио.

## 2. Ключевое обстоятельство: язык тянет за собой движок

Это главное, что надо понять до сравнения вариантов.

**faster-whisper — библиотека для Python, и только для Python.** Внутри неё лежит CTranslate2 — движок на C++, и формально его можно позвать из C++ напрямую. Но faster-whisper это не тонкая обёртка: в ней живёт фильтрация тишины через VAD, нарезка длинного аудио на окна, сборка сегментов, восстановление тайм-кодов после вырезанных пауз и защита от залипаний. Именно эта логика решает нашу исходную задачу. Взяв голый CTranslate2 из другого языка, мы пишем всё это заново.

Для C#, Rust и JS поддерживаемых привязок к CTranslate2 нет вовсе. Там доступен **whisper.cpp** — другой движок, с другим форматом моделей (GGML вместо CTranslate2), своими настройками и своим поведением.

Отсюда простое правило: **выбирая не-Python, мы одновременно выбираем whisper.cpp и выбрасываем проверенное ядро.** Не потому, что whisper.cpp плох — он хороший, — а потому, что все пройденные грабли (delay-load библиотек CUDA, namespace-пакет nvidia, подбор compute type) придётся проходить заново в другом виде.

## 3. Критерии

По убыванию важности для этого проекта:

1. **Сколько языков придётся поддерживать одному человеку.** Каждый добавленный язык — это ещё одна сборка, ещё один отладчик, ещё один набор зависимостей и целый класс ошибок на границе между ними.
2. **Сохраняется ли faster-whisper и существующее ядро.**
3. **Одинаковость поведения на трёх системах.**
4. **Стоимость упаковки** (этап M7).
5. **Размер дистрибутива** (NFR-3).
6. **Насколько знаком язык лично вам.**

Скорость самого приложения в критериях отсутствует намеренно: 99% времени работы занимает CUDA или процессор внутри движка, и им безразлично, кто их позвал. Разница между языками здесь измеряется миллисекундами на фоне часа счёта.

## 4. Варианты

### A. Python + PySide6 (Qt) — выбран

Ядро и интерфейс на одном языке, один процесс, одна сборка.

- **За:** один язык на весь проект. faster-whisper и всё готовое ядро остаются. Qt одинаково работает на трёх системах и даёт бесплатно системные диалоги файлов, поддержку экранов высокой плотности, тёмную тему, переводы. Стилизация через QSS — подмножество CSS, читается человеком с вебовым опытом.
- **Против:** собранный дистрибутив 80–150 МБ. Раскладка Qt не похожа на flexbox — привыкать. Тонкие визуальные эффекты (тени, анимации) даются тяжело.

### B. Python (ядро) + React (интерфейс) через pywebview

Ядро на Python, окно — системный веб-движок, внутри обычная веб-страница.

- **За:** интерфейс на вашем родном стеке. Готовые макеты переносятся почти один в один. Одна тяжёлая зависимость вместо двух.
- **Против:** **два языка и две сборки в проекте, который ведёт один человек.** Питоновскую половину поддерживать всё равно придётся — в ней вся суть, — так что React не заменяет Python, а добавляется к нему. Плюс pywebview заметно менее протоптан, а перетаскивание файлов в окно с получением настоящего пути — известное больное место веб-движков, его пришлось бы проверять отдельно.

### C. Electron + React + Python отдельным процессом

- **За:** самый знакомый вам мир, предсказуемая отрисовка везде одинаково.
- **Против:** три runtime в одной коробке (Chromium, Node, Python), 250+ МБ. Два языка плюс межпроцессное общение, плюс классическая беда — «один процесс умер, второй не заметил». Худший вариант по первому критерию.

### D. Tauri (Rust) + React + Python отдельным процессом

- **За:** самый маленький дистрибутив, 10–20 МБ. Хорошая работа с файлами, включая перетаскивание.
- **Против:** **три языка**, один из которых вы не знаете. Упаковка Python внутрь Tauri — нехоженая тропа. Веб-движок на Linux ведёт себя иначе, чем на двух остальных системах.

### E. C# + Avalonia + whisper.net

- **За:** строгая типизация, хорошие инструменты, приличный кроссплатформенный десктоп.
- **Против:** ядро выбрасывается целиком, движок меняется на whisper.cpp, язык вам незнаком. Выигрыша, оправдывающего это, нет.

### F. C++ + Qt + CTranslate2 напрямую

- **За:** один бинарник, максимальный контроль.
- **Против:** переписывание логики faster-whisper вручную, самая долгая разработка, самая тяжёлая поддержка. Для настольной утилиты это стрельба из пушки.

## 5. Сравнение

| | Языков в проекте | Движок | Ядро сохраняется | Сборка | Одинаковость на 3 ОС |
|---|---|---|---|---|---|
| **A. Python + Qt** | **1** | faster-whisper | **да** | 80–150 МБ | высокая |
| B. Python + React (pywebview) | 2 | faster-whisper | да | 90–160 МБ | средняя |
| C. Electron + Python | 2 | faster-whisper | да | 250+ МБ | высокая |
| D. Tauri + Python | 3 | faster-whisper | да | 30–60 МБ с Python | средняя |
| E. C# + Avalonia | 1 | whisper.cpp | **нет** | 60–80 МБ | высокая |
| F. C++ + Qt | 1 | CTranslate2 вручную | нет | 20–40 МБ | высокая |

## 6. Решение и почему именно оно

**Вариант A.**

Соблазн выбрать B или C понятен: интерфейс писался бы на знакомом языке. Но арифметика против. Тяжёлая часть проекта — ffmpeg, распознавание, анализ, экспорт — остаётся питоновской при любом раскладе, потому что там faster-whisper. Значит, React не заменяет Python, а **добавляется сверху**. Вы получаете не «проект на React», а проект на Python, плюс проект на React, плюс мост между ними — и платите двумя сборками и двумя отладчиками за знакомый синтаксис в той половине, где логики меньше всего.

Варианты E и F требуют выбросить работающее ядро ради языков, которыми вы не пользуетесь. Вариант D добавляет третий язык.

Вариант A даёт один язык, один процесс, одну сборку и сохраняет всё, что уже проверено на реальных трёх часах аудио.

## 7. Последствия

**Хорошие:**

- этап M1 сводится к переносу и перекладке готового кода, а не к переписыванию;
- отладка одна на весь проект;
- Qt закрывает собой переводы, темы, экраны высокой плотности и системные диалоги — это заметная экономия;
- вебовый опыт частично переносится: QSS читается как CSS.

**Плохие, принимаем осознанно:**

- дистрибутив 80–150 МБ вместо десятков (формулировка NFR-3 уточнена);
- дизайн придётся держать в рамках десктопного тулкита — отсюда и появился `design-brief.md`;
- раскладка Qt поначалу непривычна после flexbox.

**Что это решение не закрывает:** принципы П-1 и П-2 (ядро ничего не знает про интерфейс, зависимости идут в одну сторону) означают, что веб-интерфейс можно надстроить поверх того же ядра когда угодно. Выбор Qt — не ловушка, а первая реализация.

## 8. Когда решение стоит пересмотреть

- Если интерфейс упрётся в Qt и визуальная часть станет важнее скорости разработки — вариант B поверх того же ядра, без переписывания логики.
- Если скорость на macOS станет реальной проблемой — добавить whisper.cpp как второй движок в `core/asr/` (место оставлено), не меняя язык.
- Если появится второй разработчик с другим профилем — пересчитать первый критерий заново.
