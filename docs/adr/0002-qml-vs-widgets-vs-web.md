# ADR-0002. Система интерфейса: Qt Quick (QML)

**Статус:** принято · 16.09.2026
**Решение:** интерфейс на Qt Quick / QML, стиль собственный, не подражающий родному виду ОС
**Уточняет:** [ADR-0001](0001-language-and-stack.md), где был выбран Python + PySide6

---

## 1. Контекст

ADR-0001 выбрал Qt, но не уточнил, **какой** Qt. Внутри фреймворка живут две разные системы интерфейса, и разница между ними больше, чем между иными фреймворками:

- **Qt Widgets** — классический десктоп: готовые кнопки, таблицы, диалоги, отрисовка на процессоре. Стилизуется через QSS (подмножество CSS). Именно эта система создала Qt репутацию «программ из двухтысячных».
- **Qt Quick (QML)** — декларативный язык описания интерфейса с выражениями на JavaScript, привязками свойств и отрисовкой через сцену на видеокарте. Анимации и переходы состояний — встроенные понятия языка, а не надстройка.

Требование, из-за которого вопрос вообще возник: интерфейс не должен выглядеть устаревшим. Оно прозвучало от заказчика дважды, то есть это настоящее требование, а не пожелание.

Третий рассмотренный путь — отказаться от Qt в интерфейсе и сделать веб-страницу на React внутри системного веб-движка (pywebview), оставив ядро на Python.

## 2. Варианты

### A. Qt Widgets

- **За:** сильнейшие таблицы и деревья, максимально родной вид для каждой ОС, огромное количество примеров.
- **Против:** современный вид достигается через силу, анимации неудобны, отрисовка на процессоре. Ровно то, чего требование просит избежать.

### B. Qt Quick / QML — выбрано

- **За:** декларативное описание, привязки свойств, выражения на JavaScript — всё это близко опыту разработчика с React. Анимации и тени дёшевы, отрисовка на видеокарте, 120 кадров в секунду не подвиг. Связь с Python штатная: свойства, сигналы, слоты — прогресс обновляется сам, без ручной прокачки событий. Так сделана Cura: питоновская логика, интерфейс на QML.
- **Против:** ещё один язык, хоть и маленький. Готовых библиотек компонентов мало — ничего похожего на экосистему npm, нестандартные элементы рисуются руками. Таблицы слабее, чем в Widgets и в вебе.

### C. Python-ядро + React в системном веб-движке

- **За:** интерфейс на родном для разработчика стеке, вся экосистема npm, макеты из Claude Design переносятся почти дословно — и это экономия повторяющаяся, потому что дизайн меняется не один раз.
- **Против:** второй язык и вторая сборка в проекте, который ведёт один человек. Событий из Python в страницу нет — обратный поток собирается поверх вызовов `evaluate_js`, то есть свой слой событий, который надо писать и поддерживать. Абсолютный путь к файлу при перетаскивании в окно веб-движок не отдаёт: это защита браузера, и обходить её пришлось бы отдельно, а приложение целиком про файлы. На Linux веб-движок ведёт себя иначе, чем на двух других системах.

## 3. Решение

**Вариант B.**

Решающим оказался размер разрыва в знакомстве. Familiarity разработчика — законный инженерный довод, когда проект держится на одном человеке: от неё зависят скорость и желание возвращаться к коду. Этот довод перевесил бы, будь альтернативой язык из другого мира.

Но QML не из другого мира. Декларативные компоненты, привязки свойств, JavaScript в выражениях — это смена диалекта, а не профессии. Два-три дня на освоение против постоянного налога второго языка, второй сборки, своего слоя событий и отдельной возни с путями к файлам.

Вторая часть решения: **стиль собственный, а не подражающий родному виду системы.** Приложение будет выглядеть одинаково на Windows, macOS и Linux, как выглядят Telegram, DaVinci Resolve и Cura. Альтернатива — мимикрия под каждую ОС — даёт три разных набора макетов, втрое больше работы и всё равно не обманывает глаз.

## 4. Последствия

**Хорошие:**

- ограничения из брифа на дизайн снимаются: скругления, тени, градиенты, плавные переходы в QML дёшевы;
- прогресс и состояния приезжают в интерфейс привязками, без ручной прокачки событий;
- один процесс, один стектрейс, одна сборка;
- один набор макетов на три системы.

**Плохие, принимаем осознанно:**

- каждый нестандартный элемент интерфейса рисуется руками — готовых наборов уровня npm нет;
- сложные таблицы с сортировкой и группировкой даются тяжелее, чем в Widgets (нам они не нужны: у нас список задач, а не бухгалтерия);
- приложение не будет выглядеть «как родное» ни на одной системе — это цена единого стиля.

**Что меняется в документах:** раздел технических рамок в `design-brief.md` переписан под QML, дерево модуля `app/` в `architecture.md` перестроено под QML и объекты-мосты.

## 5. Когда пересмотреть

- Если в приложении заведётся настоящая работа с таблицами (сравнение транскриптов, редактор сегментов построчно) — рассмотреть Widgets для этого конкретного экрана, смешивать их с QML допустимо.
- Если визуальная часть станет важнее всего остального и QML начнёт мешать — вариант C поверх того же ядра, без переписывания логики. Принципы П-1 и П-2 это гарантируют.
